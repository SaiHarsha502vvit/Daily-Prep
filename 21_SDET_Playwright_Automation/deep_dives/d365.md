## 1. What D365 actually is

"Dynamics 365" is an umbrella for ~10 different products. The ones SDETs typically test:

| Product | What it is | Test surface |
|---|---|---|
| Dynamics 365 Sales | Lead/Opportunity/Quote CRM | Model-driven app |
| Dynamics 365 Customer Service | Case/Knowledge | Model-driven app |
| Dynamics 365 Field Service | Work orders, dispatch | Model-driven app + custom JS |
| Dynamics 365 Marketing | Campaigns, journeys | Real-time + Outbound surfaces (different stacks) |
| Power Apps (model-driven) | Custom CRM-style apps | Same shell as above |
| Power Apps (canvas) | Drag-and-drop apps | Different stack entirely |

The model-driven surface (Sales, Service, Field Service, Power Apps model-driven) all share the **Unified Client Interface (UCI)**. That's what you're really testing. Everything in this guide assumes UCI.

### 1.1 UCI's anatomy

```
┌────────────────────────────────────────────────────────────┐
│ Top app bar (search, settings, help)                      │
├──────────────┬─────────────────────────────────────────────┤
│              │ Command bar (New, Save, Delete, ...)        │
│ Site map     ├─────────────────────────────────────────────┤
│ (left nav)   │ Form / View / Dashboard                     │
│              │ (IFrame for model-driven forms)             │
│              │                                             │
└──────────────┴─────────────────────────────────────────────┘
```

Three different "surfaces" inside UCI, each with subtly different DOM:
- **Form** (single record) — rendered inside an IFrame (`pages-iframe-*`).
- **View** (list/grid) — `ms-DetailsList`-based grid in main DOM.
- **Dashboard** — multiple widgets, each with its own behaviour.

### 1.2 Why automation is hard

D365 fights every automation principle:

| Anti-automation property | What it means |
|---|---|
| No stable IDs by default | Element IDs are GUIDs that change |
| Hashed CSS classes | Many classes are computed at build time |
| Two-phase render | Page appears, fields populate later |
| Deep iframe nesting | Form is 2–4 frames deep |
| Async OData everywhere | Every save triggers 3–10 background calls |
| Optimistic UI lies | "Saved" toast appears before commit |
| Re-renders on focus changes | Fields re-mount; locators may go stale |
| Spinner soup | `.ms-Spinner` appears EVERYWHERE |

This guide treats each of those.

## 2. The runtime

A request to a D365 form fires:

```
1. Browser → /apps/<appid>/main.aspx?pagetype=entityrecord&etn=account&id=...
2. UCI shell loads (~3 MB of JS, ~1.5s)
3. UCI fetches form metadata via OData
4. UCI fetches the record via OData ($select=...)
5. UCI fetches related records (subgrids, lookups, BPF)
6. UCI renders the form
7. Background: telemetry, presence, navigation save, etc.
```

Steps 4–6 take 5–30 seconds in production CRM (slower with custom plugins, more fields, large records).

### 2.1 The OData endpoint

All data flows through `/api/data/v9.2/`. Examples:
- `GET /api/data/v9.2/accounts(<guid>)?$select=name,emailaddress1`
- `POST /api/data/v9.2/accounts` (create)
- `PATCH /api/data/v9.2/accounts(<guid>)` (update)
- `GET /api/data/v9.2/savedqueries?$filter=name eq 'My Active Accounts'`

For tests that need to **verify** state, hit OData directly. See [reference/06_api_testing.md](../reference/06_api_testing.md). Don't read field text from the UI for ground-truth assertions.

### 2.2 Hooks D365 fires

Custom JS, plugins, and workflows all run during form lifecycle:
- `onLoad` (form load)
- `onSave` (before save)
- `onChange` per field
- Server plugins (pre/post operation)
- Async workflows (eventually consistent)

If your tests assert on the result of an async workflow, **expect.poll** it — see [reference/08_reliability.md §5](../reference/08_reliability.md#5-expectpoll).

## 3. The two-phase render

The single most important D365 reliability concept. The reference touches this; here's the full mechanism.

### 3.1 Phase 1 — Shell

```
0.0s    Navigation request fires
0.5s    HTML shell arrives
0.7s    UCI bundle loads, initial JS runs
1.0s    Form skeleton renders (labels, empty fields, command bar)
1.0s    .ms-Spinner appears inside the form area
1.0s    domcontentloaded event fires
```

At this point: form is visually present, fields are EMPTY (`textContent === ''`).

### 3.2 Phase 2 — Data fetch and populate

```
1.0s    OData GET for the record fires
2.0s    Response arrives (varies wildly)
2.1s    UCI parses, populates fields
2.2s    Lookups fetch related labels (additional OData calls)
2.5s    Subgrids load (more OData calls)
3.0s    BPF stages compute
3.5s    .ms-Spinner disappears
3.5s    Form is fully interactive
```

Reading any field's content before phase 2 completes returns empty string or stale data.

### 3.3 The canonical wait

```typescript
async function waitForD365Load(page: Page, expectedTitle?: string): Promise<void> {
  // 1. Every spinner gone (this is the strict gate)
  await expect(page.locator('.ms-Spinner')).toHaveCount(0, { timeout: 45_000 });

  // 2. Verify the right record (anti-stale-render)
  if (expectedTitle) {
    const titleArea = page.locator('.ms-CommandBar, .ms-PageHeader, h1[title]').first();
    await expect(titleArea).toContainText(expectedTitle, { timeout: 30_000 });
  }
}
```

> Always pair "spinner gone" with a content check. Spinners go and come; a fresh navigation may have spinners-gone-then-coming-back in the brief window between.

### 3.4 The stale-render scenario in depth

When you navigate from Account A to Account B:

```
0.0s    User clicks "Account B" in the view
0.0s    URL changes to /accounts(<B>)
0.1s    UCI begins teardown of A's form
0.2s    UCI sets up B's form shell
        ↑ At this moment, the form might briefly show A's data
0.3s    Spinner appears
0.5s    OData fetch for B fires
2.0s    B's data populates
2.0s    Spinner disappears
```

A test that reads "name" field at 0.2s gets A's name. A test that asserts `toHaveText('B')` retries until 2.0s and passes.

Always use auto-retrying assertions:
- `await expect(field).toHaveText('Expected B', { timeout: 30_000 })` ✅
- `expect(await field.textContent()).toBe('Expected B')` ❌

### 3.5 The spinner-vs-overlay ladder

`.ms-Spinner` is the granular spinner. There's also:

| Class | When it appears |
|---|---|
| `.ms-Spinner` | Per-section data fetch |
| `.ms-Overlay` | Whole-form overlay during save |
| `.lcid-loadingScreen` | Initial app boot |
| `.ms-MessageBar--blocking` | "This page is unresponsive" prompt |
| `[role="progressbar"]` | ARIA-compliant fallback in some versions |

The robust wait covers them all:

```typescript
await expect(page.locator('.ms-Spinner, .ms-Overlay, [role="progressbar"]')).toHaveCount(0, { timeout: 45_000 });
```

## 4. The Fluent UI class taxonomy

The `.ms-` prefix is Microsoft's Fluent UI namespace. The classes you'll actually fight with:

### 4.1 Structural

| Class | Element type |
|---|---|
| `.ms-Layer` | Floating layer (dropdowns, tooltips, dialogs) |
| `.ms-Callout` | Specific floating panel (date pickers, color pickers) |
| `.ms-Modal` | Full modal dialog |
| `.ms-Panel` | Side-sliding panel |
| `.ms-Overlay` | Page-blocking overlay |
| `.ms-Fabric` | Root container |

### 4.2 Form controls

| Class | Element type |
|---|---|
| `.ms-TextField` | Text input wrapper |
| `.ms-Dropdown` | Custom select |
| `.ms-Dropdown-callout` | Dropdown's option list |
| `.ms-Dropdown-item` | Individual option |
| `.ms-DatePicker` | Date picker |
| `.ms-Calendar` | The calendar inside it |
| `.ms-ChoiceField` | Radio group / checkbox group |
| `.ms-Checkbox` | Single checkbox |
| `.ms-Toggle` | Boolean switch |
| `.ms-ComboBox` | Combo with type-ahead |
| `.ms-Lookup` | Lookup field (see §8) |

### 4.3 Grids and lists

| Class | Element type |
|---|---|
| `.ms-DetailsList` | The grid container |
| `.ms-DetailsList-headerWrapper` | Column header row |
| `.ms-DetailsList-contentWrapper` | Body rows container |
| `.ms-DetailsRow` | A row (modern) |
| `.ms-DetailsList-row` | A row (older variant — both can appear) |
| `.ms-DetailsRow-cell` | A cell |
| `.ms-Selection-checkmark` | Row checkmark |
| `.ms-DetailsHeader-cell` | Column header |
| `.ms-DetailsList-stickyTrailingRow` | Footer (totals row) |

### 4.4 Command surfaces

| Class | Element type |
|---|---|
| `.ms-CommandBar` | The top bar (New, Save, etc.) |
| `.ms-CommandBarItem` | A button inside |
| `.ms-ContextualMenu` | Right-click menu |
| `.ms-ContextualMenu-item` | Option in context menu |
| `.ms-Nav` | Site map / navigation |
| `.ms-Nav-link` | Site map link |

### 4.5 Feedback

| Class | Element type |
|---|---|
| `.ms-MessageBar` | Inline message (info/warning/error/success) |
| `.ms-MessageBar--error` | Error variant |
| `.ms-MessageBar--success` | Success variant |
| `.ms-Spinner` | Granular spinner |
| `.ms-TeachingBubble` | Onboarding tooltip |

### 4.6 Why this matters

Most tests don't NEED these classes — `getByRole('button', { name: 'Save' })` works without knowing it's `.ms-CommandBarItem`. But when ARIA fails (custom widgets without proper roles), this taxonomy is your fallback.

**Order of preference:**

```typescript
// Best
page.getByRole('button', { name: 'Save' })

// OK fallback
page.locator('button[data-id="account|NoRelationship|Form|Mscrm.Form.account.SaveAndClose"]')

// Last resort
page.locator('.ms-CommandBarItem').filter({ hasText: 'Save' })
```

## 5. Entity forms

D365 entity forms come in three flavours:

### 5.1 Main form

The full form when you open a record. URL: `/main.aspx?pagetype=entityrecord&etn=account&id=...`.

Rendered inside an IFrame (see §6). Has a command bar, tabs, sections, fields, and often a BPF (§10).

Test pattern:

```typescript
async function openAccount(page: Page, accountId: string): Promise<FrameLocator> {
  await page.goto(`/main.aspx?pagetype=entityrecord&etn=account&id=${accountId}`);
  const formFrame = page.frameLocator('iframe[name^="pages-iframe"]');
  await waitForD365LoadInFrame(formFrame, 'Account Name'); // see §3.3 adapted
  return formFrame;
}
```

### 5.2 Quick Create

A side-panel form with only essential fields. Triggered by "+ New" on the command bar of a related entity.

```typescript
await formFrame.getByRole('menuitem', { name: 'New Contact' }).click();
const quickCreate = page.locator('.ms-Panel');
await expect(quickCreate).toBeVisible();
await quickCreate.getByLabel('First Name').fill('Alice');
await quickCreate.getByLabel('Last Name').fill('Smith');
await quickCreate.getByRole('button', { name: 'Save and Close' }).click();
```

Quick Create has its OWN `.ms-Spinner` cycle, separate from the parent form's.

### 5.3 Quick View

A read-only sub-form embedded inside a main form (e.g., "Primary Contact" details shown inside an Account form).

```typescript
const quickView = formFrame.locator('[data-id^="QuickViewControl"]');
await expect(quickView.getByLabel('Email')).toHaveText('contact@example.com');
```

Quick View loads asynchronously AFTER the main form. Add an extra wait if asserting on its contents.

## 6. The form IFrame nesting

Model-driven app forms are wrapped in IFrames. Depth varies:

```
page (top)
└── iframe[name="contentPanel"]              (sometimes — depends on shell version)
    └── iframe[name^="pages-iframe"]          (the form host)
        └── iframe[name^="WebResource_"]      (custom web resources, if any)
```

Most modern UCI puts the form in ONE IFrame, named `pages-iframe-<number>`. The number changes per session.

### 6.1 The reliable frame locator

```typescript
const formFrame = page.frameLocator('iframe[name^="pages-iframe"]');
```

`name^="pages-iframe"` is a CSS attribute-starts-with selector. Survives the numeric suffix change.

### 6.2 When forms have nested web resources

Custom HTML web resources (legacy ASP.NET pages embedded as form sections) live in additional IFrames:

```typescript
const formFrame = page.frameLocator('iframe[name^="pages-iframe"]');
const customSection = formFrame.frameLocator('iframe[name="WebResource_legacyform"]');
await customSection.locator('#oldButton').click();
```

Each `frameLocator` returns a fresh `FrameLocator` you can chain.

### 6.3 The "no iframe" view surfaces

Views (the grid surface), dashboards, and the global search are NOT in iframes. They live in the main page.

```typescript
// View
const grid = page.locator('.ms-DetailsList');

// Form (in frame)
const formFrame = page.frameLocator('iframe[name^="pages-iframe"]');
const grid = formFrame.locator('.ms-DetailsList');   // subgrid inside the form
```

Knowing which surface you're on determines whether you need `frameLocator` or not.

### 6.4 Cross-frame action coordination

If your test action triggers something in the parent (e.g., a save in the form refreshes the parent's left nav):

```typescript
// Save in the form frame
await formFrame.getByRole('menuitem', { name: 'Save' }).click();

// Wait for parent to react
await expect(page.locator('.ms-Nav').getByText('Updated Account')).toBeVisible({ timeout: 10_000 });
```

The parent and frame are independent DOMs. Auto-wait per-frame, not cross-frame.

## 7. Field types

Each D365 field type behaves differently. The fill patterns:

### 7.1 Text (single line)

```typescript
const field = formFrame.locator('[data-id="name"] input, [data-id="name"] textarea').first();
await field.fill('Contoso Ltd');
await field.blur();   // critical — D365 commits on blur, not on input
```

Without `blur()`, the value is in the DOM but not in D365's dirty-state tracker. Save will think nothing changed.

### 7.2 Text (multi-line)

```typescript
const field = formFrame.locator('[data-id="description"] textarea');
await field.fill('Long description...\nWith line breaks.');
await field.blur();
```

### 7.3 Number / Currency

```typescript
const field = formFrame.locator('[data-id="creditlimit"] input');
await field.fill('50000');
await field.blur();
```

D365 formats numbers on blur (`50,000.00 USD`). Re-reading immediately shows the formatted value. Compare semantically:

```typescript
const value = await field.inputValue();
expect(value.replace(/[^\d.]/g, '')).toBe('50000.00');
```

### 7.4 Date

```typescript
const field = formFrame.locator('[data-id="estimatedclosedate"] input');
await field.fill('1/15/2026');           // depends on user locale
await field.blur();
```

Date format depends on user's D365 settings. For cross-environment tests, set the user's locale to a known value, OR use ISO and let D365 parse:

```typescript
await field.fill('2026-01-15');
```

Most D365 instances accept ISO. Test it in your env first.

### 7.5 Date+Time

```typescript
const field = formFrame.locator('[data-id="lastonholdtime"] input');
await field.fill('1/15/2026 10:30 AM');
await field.blur();
```

The time field is often a separate input next to the date:

```typescript
const dateField = formFrame.locator('[data-id="duedate"] input').first();
const timeField = formFrame.locator('[data-id="duedate"] input').nth(1);
await dateField.fill('1/15/2026');
await timeField.fill('10:30 AM');
await timeField.blur();
```

### 7.6 Option Set (single)

A custom dropdown, not a `<select>`:

```typescript
const dropdown = formFrame.locator('[data-id="industrycode"] [role="combobox"]');
await dropdown.click();

// The option list renders at the TOP-LEVEL page, OUTSIDE the iframe
const option = page.getByRole('option', { name: 'Banking' });
await option.click();
```

Critical: the dropdown control is INSIDE the frame; the options list renders OUTSIDE the frame in a `.ms-Callout` layer. Don't try `formFrame.getByRole('option', ...)` — it won't find anything.

### 7.7 Option Set (multi-select)

Same pattern but the popover allows multi-select. Click options without closing:

```typescript
await dropdown.click();
await page.getByRole('option', { name: 'Banking' }).click();
await page.getByRole('option', { name: 'Finance' }).click();
await page.keyboard.press('Escape');  // close the popover
```

### 7.8 Two-Option (Yes/No)

```typescript
const toggle = formFrame.locator('[data-id="donotemail"] [role="switch"]');
const currentState = await toggle.getAttribute('aria-checked');
if (currentState === 'false') {
  await toggle.click();
}
```

Toggle behaviour — click flips. Always check current state if you need a specific value.

### 7.9 Lookup field

See §8 — this is the worst.

### 7.10 Customer (polymorphic lookup)

A "Customer" field can point to EITHER an Account OR a Contact. The lookup popover lets you switch:

```typescript
const customerField = formFrame.locator('[data-id="customerid"] input');
await customerField.click();
await page.getByRole('button', { name: 'Change record type' }).click();
await page.getByRole('menuitem', { name: 'Contact' }).click();
await page.getByRole('option', { name: 'Alice Smith' }).click();
```

## 8. Lookup fields

The single most painful D365 field type. A lookup is a typeahead that resolves to a related record.

### 8.1 The structure

```html
<div data-id="primarycontactid">
  <input role="combobox" aria-haspopup="dialog">  <!-- type-ahead input -->
  <button>Browse</button>                          <!-- opens a full picker -->
  <!-- When you type, suggestions appear in a .ms-Callout at the top level -->
</div>
```

Two ways to set a value:
1. Type-ahead — fill the input, wait for suggestions, click one.
2. Browse — click Browse, opens a record picker dialog.

### 8.2 Type-ahead pattern

```typescript
async function setLookup(formFrame: FrameLocator, dataId: string, searchTerm: string, expectedResult: string): Promise<void> {
  const field = formFrame.locator(`[data-id="${dataId}"] input[role="combobox"]`);
  await field.click();
  await field.fill(searchTerm);
  
  // Suggestions render in a flyout at TOP-LEVEL (not in frame)
  // page.getByRole('listbox') OR page.locator('.ms-Suggestions')
  const suggestion = page.getByRole('option', { name: expectedResult });
  await expect(suggestion).toBeVisible({ timeout: 10_000 });
  await suggestion.click();

  // Wait for the lookup to commit
  await expect(field).toHaveValue(expectedResult, { timeout: 5_000 });
}

// Usage
await setLookup(formFrame, 'primarycontactid', 'Alice', 'Alice Smith');
```

### 8.3 The "already has a value" trap

If the field already has a value, typing replaces it. Clear first:

```typescript
const field = formFrame.locator(`[data-id="primarycontactid"] input`);
await field.click();
await field.press('Control+A');
await field.press('Delete');
// Now type the new value
```

### 8.4 The "no results" race

If `setLookup` is called too quickly after page load, OData might still be initialising the field's lookup view. The search returns zero results:

```typescript
async function setLookupWithRetry(formFrame, dataId, searchTerm, expectedResult): Promise<void> {
  await expect.poll(async () => {
    const field = formFrame.locator(`[data-id="${dataId}"] input`);
    await field.click();
    await field.fill(searchTerm);
    return await page.getByRole('option', { name: expectedResult }).isVisible();
  }, { timeout: 30_000, intervals: [1000, 2000, 5000] }).toBe(true);

  await page.getByRole('option', { name: expectedResult }).click();
}
```

### 8.5 The Browse dialog

```typescript
await formFrame.locator('[data-id="primarycontactid"] button[aria-label="Browse"]').click();
const dialog = page.getByRole('dialog');
await expect(dialog).toBeVisible();

// Search in the dialog
await dialog.getByPlaceholder('Search').fill('Alice');
await dialog.getByRole('row', { name: 'Alice Smith' }).click();
await dialog.getByRole('button', { name: 'Add' }).click();
await expect(dialog).not.toBeVisible();
```

### 8.6 Lookup view scoping

Lookups respect "lookup views" — saved filters that limit what records are searchable. If your test data isn't in the lookup view, suggestions return nothing. Either:
- Adjust the lookup view in test setup.
- Use the Browse dialog and switch to "Look in: All".

### 8.7 Clearing a lookup

```typescript
const field = formFrame.locator(`[data-id="primarycontactid"]`);
await field.locator('button[aria-label="Delete"]').click();
```

Or programmatically:

```typescript
await page.evaluate((id) => {
  const Xrm = (window as any).Xrm;
  Xrm.Page.getAttribute(id).setValue(null);
}, 'primarycontactid');
```

`Xrm.Page` is D365's client API. Faster than UI, but bypasses validation. Use for setup, not for behaviour tests.

## 9. Subgrids

A subgrid is a `.ms-DetailsList` embedded in a form. Lists related records (e.g., Contacts on an Account form).

### 9.1 Identifying the subgrid

```typescript
const subgrid = formFrame.locator('[data-id="Contacts"]');
const grid = subgrid.locator('.ms-DetailsList');
const rows = grid.locator('.ms-DetailsRow, .ms-DetailsList-row');  // both class variants
```

### 9.2 Common operations

```typescript
// Count rows
const count = await rows.count();

// Find a specific row by content
const aliceRow = rows.filter({ hasText: 'Alice Smith' });

// Click the row
await aliceRow.click();

// Click a cell in the row
await aliceRow.locator('[data-id="emailaddress1"]').click();
```

### 9.3 Adding a new related record

```typescript
// From the subgrid's local command bar
await subgrid.getByRole('menuitem', { name: 'New Contact' }).click();

// Quick Create opens
const quickCreate = page.locator('.ms-Panel');
await quickCreate.getByLabel('First Name').fill('Bob');
await quickCreate.getByLabel('Last Name').fill('Jones');
await quickCreate.getByRole('button', { name: 'Save and Close' }).click();

// Wait for subgrid to refresh
await expect(rows.filter({ hasText: 'Bob Jones' })).toBeVisible({ timeout: 10_000 });
```

### 9.4 The "subgrid not loading" race

Subgrids load AFTER the main form fields. On a freshly opened record:

```typescript
await waitForD365Load(formFrame, 'Contoso Ltd');                    // form ready
await expect(subgrid.locator('.ms-Spinner')).toHaveCount(0, { timeout: 30_000 });  // subgrid ready
```

### 9.5 Virtualised rows

Large subgrids virtualise — only ~20 visible rows are in the DOM. To find a row in a 500-row grid:

```typescript
// Search via the subgrid's filter
await subgrid.locator('input[placeholder*="Search"]').fill('Alice');
await expect(rows).toHaveCount(1);
```

Don't try to scroll to find rows — virtualised lists are not reliably scrollable through automation.

## 10. Business Process Flow

A BPF is a multi-stage workflow displayed at the top of a form. Each stage has fields the user fills before advancing.

### 10.1 BPF anatomy

```
[ Qualify ] → [ Develop ] → [ Propose ] → [ Close ]
                ↑ current stage (highlighted)
                
Current stage panel:
  - Field 1: ____
  - Field 2: ____
  - [Next Stage] button
```

### 10.2 Locating stages

```typescript
const bpf = formFrame.locator('[data-id^="header_process"]');
const stages = bpf.locator('[role="button"][aria-label]');

// All stage labels
const stageLabels = await stages.allTextContents();
// ['Qualify', 'Develop', 'Propose', 'Close']

// The current stage (has aria-current="step")
const currentStage = stages.filter({ has: page.locator('[aria-current="step"]') });
```

### 10.3 Setting stage fields

```typescript
const stagePanel = formFrame.locator('[data-id="header_process_stage_panel"]');
await stagePanel.getByLabel('Need identified').click();   // option set in BPF
await stagePanel.getByLabel('Purchase amount').fill('50000');
```

### 10.4 Advancing the stage

```typescript
await stagePanel.getByRole('button', { name: 'Next Stage' }).click();
await expect(stagePanel.getByText('Develop')).toBeVisible({ timeout: 10_000 });
```

### 10.5 BPF on a different entity

A BPF can span entities (an Opportunity BPF might have a "Quote" stage that lives on the Quote entity). Advancing the stage navigates the form away from the current record. Handle:

```typescript
const [navigationFinish] = await Promise.all([
  page.waitForURL(/etn=quote/),
  stagePanel.getByRole('button', { name: 'Next Stage' }).click(),
]);
```

## 13. Save semantics

D365 has multiple save flows:

### 13.1 Save (Ctrl+S)

```typescript
await formFrame.getByRole('menuitem', { name: 'Save' }).click();
// OR
await page.keyboard.press('Control+s');
```

Stays on the same record. UI shows "Saving..." spinner briefly. URL doesn't change.

### 13.2 Save & Close

```typescript
await formFrame.getByRole('menuitem', { name: 'Save & Close' }).click();
// URL navigates BACK to the view that opened this record
await page.waitForURL(/pagetype=entitylist/);
```

### 13.3 Save & New

```typescript
await formFrame.getByRole('menuitem', { name: 'Save & New' }).click();
// URL navigates to a NEW (empty) record of the same entity
await page.waitForURL(/etn=account.*id=00000000-0000-0000-0000-000000000000/);
```

### 13.4 Auto-Save

If the org has auto-save enabled (default), forms save automatically 30 seconds after a change. This causes test races:

```
0s    Fill name field
0s    Fill phone field  
0s    Assert phone field has value
30s   Auto-save fires
30s   Spinner appears mid-test
35s   Spinner gone
```

For tests, either:
- Save explicitly (preferred — deterministic).
- Disable auto-save in test environment.
- Build waits that survive mid-test spinners.

### 13.5 Verifying the save committed

UI says "Saved" — but did the OData call succeed?

```typescript
await formFrame.getByRole('menuitem', { name: 'Save' }).click();

// Wait for the save's spinner cycle
await expect(formFrame.locator('.ms-Spinner')).toHaveCount(0, { timeout: 30_000 });

// Cross-validate with OData
const accountId = new URL(page.url()).searchParams.get('id')!;
const fresh = await request.get(`${env.D365_URL}/api/data/v9.2/accounts(${accountId})?$select=name`);
expect((await fresh.json()).name).toBe('Expected Name');
```

See [reference/12_data.md §11](../reference/12_data.md#11-three-layer-verification).

## 14. Optimistic concurrency

D365 uses ETag-based optimistic concurrency. If two users edit the same record:

```
User A: opens record, reads version=5
User B: opens record, reads version=5
User A: saves → version=6
User B: saves → ETag mismatch → "Record was modified by another user. Refresh and try again."
```

### 14.1 In test parallelism

Two tests writing to the same record in different workers will trigger this. Tests randomly fail with "Record was modified" — flake.

### 14.2 The fix

| Strategy | Detail |
|---|---|
| One record per test | Use UUIDs; never share records across tests |
| Account pool | Tests claim a record exclusively for their duration |
| describe.serial | If tests truly need the same record, serialise |

UUIDs are the simplest correct approach.

### 14.3 Handling the dialog when it appears

```typescript
// If you must allow the race, handle the dialog
page.on('dialog', dialog => {
  if (dialog.message().includes('was modified')) {
    dialog.accept();
    // Then reload and retry
  }
});
```

This is a band-aid. The real fix is test isolation.

## 15. Notifications

D365 notifications come in a stack:

| Notification | Class / Role |
|---|---|
| Inline form notification | `.ms-MessageBar` inside the form |
| Toast notification | `[role="status"]` at the bottom-right |
| Modal alert dialog | `[role="alertdialog"]` blocks the form |
| Confirmation dialog | `[role="alertdialog"]` with Yes/No |
| BPF stage validation message | Inside the BPF panel |

### 15.1 Form notifications

```typescript
const notifications = formFrame.locator('.ms-MessageBar');

// Wait for success notification after save
await expect(notifications).toContainText('Saved', { timeout: 10_000 });

// Assert no errors
await expect(notifications.filter({ has: page.locator('.ms-MessageBar--error') })).toHaveCount(0);
```

### 15.2 Toast notifications

```typescript
const toast = page.getByRole('status');
await expect(toast).toContainText('Updated successfully');
```

Toasts auto-dismiss after ~3s. Don't try to interact AFTER they're gone.

### 15.3 Alert dialogs

```typescript
const confirmDialog = page.getByRole('alertdialog');
await expect(confirmDialog).toContainText('Are you sure you want to delete?');
await confirmDialog.getByRole('button', { name: 'Yes' }).click();
```

### 15.4 Workflow validation message ladder

When a user tries to advance a BPF stage with missing fields:

```
1. Inline field error appears next to the missing field
2. Form-level message bar appears: "Please fill required fields"
3. BPF stage shows a red exclamation icon
```

To detect:

```typescript
const fieldErrors = formFrame.locator('[role="alert"]');
const count = await fieldErrors.count();
if (count > 0) {
  throw new Error(`Form has ${count} validation errors`);
}
```

## 16. Per-entity cookbook

Different entities have different quirks. Highlights:

### 16.1 Account

- Has a Customer-type "Parent Account" lookup (polymorphic — see §7.10).
- Often customised with industry-specific fields.
- BPF for opportunities is anchored on Account.

### 16.2 Contact

- "Parent Customer" can be Account OR Contact.
- "Job Title" is text but commonly suggests from a list.
- Activity timeline (Calls, Emails, Tasks) is async-loaded — expect 5+ seconds.

### 16.3 Opportunity

- BPF with up to 4 stages.
- "Estimated Close Date" is required by default; tests often hit this.
- "Probability" is auto-computed from BPF stage.

### 16.4 Lead

- Lead → Account/Contact/Opportunity "Qualify" is a one-way conversion.
- After qualifying, the Lead is read-only.

### 16.5 Case

- Has subgrids for related cases, knowledge articles.
- "Resolve" action navigates to a modal form.
- SLA timer in the header counts down.

### 16.6 Activities (polymorphic)

Phone Call, Email, Task, Appointment all share the Activity entity. Each has its own form. Subgrids on records typically show "Activities" as a unified list:

```typescript
const activities = formFrame.locator('[data-id="Timeline"]');
await activities.locator('[role="button"][aria-label="Create record"]').click();
await page.getByRole('menuitem', { name: 'Phone Call' }).click();
```

## 17. The command bar

The command bar's button visibility depends on:
- Entity type
- Record state (active vs inactive)
- User role and permissions
- Form context (Create vs Edit vs Read-Only)
- Custom rules

Tests should never assume a button is present. Always check:

```typescript
const saveButton = formFrame.getByRole('menuitem', { name: 'Save' });
if (await saveButton.isVisible()) {
  await saveButton.click();
} else {
  // Maybe there's a "Save and Close" instead
  await formFrame.getByRole('menuitem', { name: 'Save & Close' }).click();
}
```

### 17.1 The overflow menu

Command bars hide buttons when they don't fit. Overflow items are under "...":

```typescript
await formFrame.getByRole('menuitem', { name: 'More commands' }).click();
const overflow = page.getByRole('menu');
await overflow.getByRole('menuitem', { name: 'Deactivate' }).click();
```

This appears in narrow viewports. Tests that work at 1440x900 might fail at 1280x720 because buttons shifted into overflow.

### 17.2 Async command buttons

Some commands trigger an OData call before doing anything:

```typescript
await formFrame.getByRole('menuitem', { name: 'Qualify' }).click();
// Spinner appears while the qualify operation runs
await expect(formFrame.locator('.ms-Spinner')).toHaveCount(0, { timeout: 60_000 });
// Then a dialog asks for confirmation
const dialog = page.getByRole('dialog');
await expect(dialog).toBeVisible();
```

## 18. Performance

D365 tests are slow. Realistic numbers:

| Operation | Time |
|---|---|
| Initial app load (cold) | 8–15 s |
| Initial app load (warm) | 3–6 s |
| Form load (new) | 2–4 s |
| Form load (existing record) | 4–10 s |
| Subgrid load | 1–3 s |
| Save (small record) | 1–2 s |
| Save (with workflows) | 3–10 s |
| Qualify lead | 5–15 s |

A 10-step end-to-end test against D365 typically runs 60–120 seconds. Budget accordingly.

### 18.1 Speedups

| Technique | Impact |
|---|---|
| storageState (skip login) | Saves 8–15s/test |
| API setup (skip UI for data creation) | 30s → 200ms |
| Disable D365's auto-save in test env | Removes mid-test spinner races |
| Pre-cache the user's UCI bundle | Saves 2–3s on each test (first navigation) |
| Skip BPF advancement (set stages via API) | 5–15s saved per stage |

### 18.2 Test budget calculation

For a 200-test D365 suite with avg 90s per test:
- Sequential: 200 × 90s = 5 hours
- 4 workers: 5h / 4 = 75 min
- 4 shards × 4 workers: 75 / 4 = 19 min

For more speed, increase shards or move more setup to API.

## 19. Common production failures

### Failure 1 — Field is empty after navigation

**Symptom:** `await formFrame.locator('[data-id="name"]').textContent()` returns empty.

**Cause:** Two-phase render — read before populate.

**Fix:** `await expect(formFrame.locator('[data-id="name"]')).toHaveText(/./, { timeout: 30_000 })`.

### Failure 2 — Lookup suggestion not visible

**Symptom:** Type in lookup, no suggestions appear.

**Cause:** Suggestions render OUTSIDE the iframe in a top-level layer.

**Fix:** `page.getByRole('option', ...)`, not `formFrame.getByRole(...)`.

### Failure 3 — Save says "Record was modified by another user"

**Symptom:** Random failure with that dialog.

**Cause:** Optimistic concurrency violation — two tests editing same record.

**Fix:** Per-test UUIDs or account pool.

### Failure 4 — Spinner-hidden-then-coming-back races

**Symptom:** Test waits for spinner gone, proceeds, then a NEW spinner starts as the page enters phase 2.

**Cause:** Phase 1 spinner gone briefly between shell render and OData fetch.

**Fix:** Combine spinner wait WITH a content check.

### Failure 5 — Test fails at narrow viewport

**Symptom:** Works at 1440x900; fails at 1280x720 because the command button is in overflow.

**Fix:** Set viewport explicitly in config. Or always check overflow if button isn't visible.

### Failure 6 — Subgrid contains stale data

**Symptom:** Added a record; subgrid doesn't show it.

**Cause:** Subgrid wasn't refreshed.

**Fix:** Click the refresh button OR re-navigate to force reload.

### Failure 7 — "Save and Close" doesn't close

**Symptom:** Click Save & Close; form stays.

**Cause:** A validation error prevented save; UI swallowed the error.

**Fix:** Check for `.ms-MessageBar--error` after every Save.

### Failure 8 — Test data accumulates ("Test Account" everywhere)

**Symptom:** Production support sees 5000 Test Accounts in real D365.

**Cause:** Test environment not properly isolated; tests run against production.

**Fix:** Strict environment separation. Tag with `testFlag`. Sweeper.

### Failure 9 — IFrame timeout on subsequent tests

**Symptom:** First test passes. Second test times out waiting for iframe.

**Cause:** Previous test left a modal open that intercepts navigations.

**Fix:** afterEach cleanup that dismisses dialogs and navigates to home.

### Failure 10 — Auto-save triggers mid-test

**Symptom:** Mid-test spinner; test fails because it's clicking through it.

**Cause:** 30s auto-save fired.

**Fix:** Disable auto-save in test env, OR keep tests under 25s, OR add spinner wait between every step.

## 20. Anti-pattern catalog

| ❌ | ✅ |
|---|---|
| `getByRole('button', { name: 'Edit' })` for D365 command bar | `getByRole('menuitem', { name: 'Edit' })` |
| `textContent()` reads in two-phase render | `expect(loc).toHaveText(...)` |
| `formFrame.getByRole('option', ...)` for lookup popovers | `page.getByRole('option', ...)` (top-level) |
| `waitForTimeout(5000)` for D365 load | `expect(spinner).toHaveCount(0)` + content check |
| Reading from UI for ground truth | OData call for ground truth |
| Hardcoded record IDs in parallel tests | UUIDs |
| Sharing test records across tests | Per-test records |
| Auto-save enabled in test env | Disabled |
| Fill field without blur | Always `.blur()` after `.fill()` for text fields |
| Subgrid scroll to find row | Use subgrid filter |
| Asserting on toast text after it auto-dismissed | Snapshot the assertion before dismiss timeout |
| One huge POM for whole entity | Component POMs per section (header, BPF, subgrid) |
